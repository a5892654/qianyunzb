# 源画面性能优化与验证

2026-10-31，Windows 本机验证。基线提交：`f4ea8d1c7dd2db2c61d7cae4b2f371b9e56a88d5`。

## 已实施

- 源画面改为 BGRA 共享内存 → 原生 GDI 窗口，移除该路径的 JPEG 压缩、HTTP 与 WebView2 解码。原有 `/source` 网页入口继续兼容。
- 单槽最新帧与事件唤醒；窗口消费慢时丢弃过期画面，采集不等待显示线程，不积累队列。静止画面不重复发布。
- 网页 JPEG 仅在预览请求存在时生成，复用 BGR 缓冲；预览关闭约 1.5 秒后停止压缩。
- 皮套按实际新帧和尺寸缓存缩放结果、透明包围盒与混合权重；OpenCV 原位混合保留输出 alpha。
- OpenCV 最多使用两个工作线程，降低与游戏及语音引擎的 CPU 争用。首帧验证通过后不再反复缩到 16×9 检查黑屏。
- 字幕按文字和宽度缓存，保留开关和说完后的停留时间；直接推流与旧网页字幕不重复叠加。
- 显示子进程使用独立 DPI 感知，通过源窗口实际 DPI 校准尺寸；采集进程的 DPI 模式保持原有行为。
- 停止时释放共享对象；源窗口监听生产进程退出，生产进程异常退出后不残留源窗口。

## 基准结果

1920×1080、目标 30 FPS，固定随机种子，两个交替游戏画面与 720px 透明皮套，预热 10 帧、记录 120 帧。网页预览关闭。表中为 **CPU 侧采集回调处理、合成与帧交付的耗时中位数**。

| 场景 | 优化前 | 优化后 | 耗时下降 |
|---|---:|---:|---:|
| 皮套每帧变化 | 16.281 ms | 6.977 ms | 57.1% |
| 复用相同皮套帧，游戏持续变化 | 16.116 ms | 4.906 ms | 69.6% |

变化皮套场景的 p95 从 17.098 ms 降到 7.678 ms。基线 OpenCV 使用 32 个线程，优化后使用 2 个。

本基准未计入真实 WGC/GPU 回读、Live2D 浏览器渲染及 PNG 读回、原生窗口 GDI 显示、原网页解码、游戏、音频或直播软件编码。因此上述百分比仅描述这些 CPU 帧处理阶段，不表示整机占用或实际直播延迟下降同等比例。尚未进行真实平台推流测试。

已保存的原始数据：[source_performance_2026-10-31.json](benchmarks/source_performance_2026-10-31.json)。在项目根目录复现（结果写入 `outputs/source_performance.json`）：

```powershell
.venv\Scripts\python.exe tools\benchmark_source_pipeline.py --baseline-ref f4ea8d1c7dd2db2c61d7cae4b2f371b9e56a88d5
```

## 验证

94 项采集、原生窗口、共享内存、皮套、主题、字幕与白饭回归通过；另有 52 项直播编排离线检查通过。原生窗口使用真实 Windows Graphics Capture 验证了 1920×1080 尺寸、准确的像素颜色、被另一窗口遮挡后的持续更新和退出清理。DPI 校准还覆盖了游戏边框导致的缩放估算误差。

```powershell
.venv\Scripts\python.exe -m unittest tools.verify_source_performance tools.verify_source_window tools.verify_live2d_overlay tools.verify_stream_theme tools.verify_rice
```

## 使用

重启千音，重新开启源画面，在直播姬采集“千音源画面”。直播时切回控制台，避免网页预览持续压缩 JPEG。源窗口可以被游戏遮挡，请保持开启、不要最小化。直播姬画布与输出均保持 1920×1080，避免再次缩放。
